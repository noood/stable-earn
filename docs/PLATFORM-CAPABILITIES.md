# 平台 API 能力盘点与同步规则

**目的：**逐平台检查四种资产（USDT、USDC、USDGO、BTC）的活期与定期产品信息/APR、持仓是否有可用 API；据此配置日常同步。本文件维护已核验能力与证据；空、部分、失败、缓存和归档行为以[数据状态规则](DATA-STATES.md)为准，字段解析以[APR 与额度规则](API-APR-CAPACITY-RULES.md)为准。产品/APR 行的“最近结果”同时记录本次回包里的利率、档位和额度字段，不另维护重复产品明细表。

**能力矩阵**记录“项目对这个字段有没有可用 API”以及“日常同步是否已接入”。它不是具体产品目录：产品 ID、APR、额度档、期限和资格仍来自产品接口的每次响应。`public` 是公开接口，`authenticated` 需要已保存的账号凭证；“项目没有可用接口”表示按项目当前范围改由手动维护，不宣称交易所绝无任何其他产品线或未来接口。

## 全量逐项能力表（112 项）

本表按“7 个展示平台 × 4 种资产 × 活期/定期 × 产品/APR、持仓”逐项列出，共 112 项。代码中有 8 个平台注册/地区账号条目；总览将 MEXC PH、UK 合并为一个展示平台，所以是 7 组。最近检查日期只说明端点或公开产品目录何时核验；鉴权持仓的账户结果不在本表公开。MEXC 的 PH、UK 依据分别列在同一行。日常接入状态来自代码能力配置，不由检查结果推断。

**“是否支持 API”的口径：**依据项目已核验并配置的接口能力与适用范围；有可用接口即标“支持”，没有项目可用接口才标“不支持”。某次请求为空、未配置凭证、暂时失败或只返回部分数据，不会改变这项能力结论；这些情况单独记录在“最近结果”。产品/APR 行中，`有数据` 后分项列产品 APR、档位边界、额度字段和资格；成功但空统一写“没有返回该币种产品”。

持仓接口数据用于计算收益、额度占用，并在完整快照中判断是否归零。OKX 接口只返回币种汇总、不提供产品 ID；但项目每个受监控币种只跟踪一条 OKX 活期产品，因此完整有效的币种结果可一对一映射，缺少币种行按零持仓处理。持仓行的“最近结果”只记录接口状态，不写入金额、条数或产品明细：“完整读取”表示本次列表读完且字段检查通过，不代表账户有持仓；部分数据和请求失败会分别标明。未接入的范围仍注明“未查询：项目无可用接口”。

## 空、部分、失败及目录处理规则

以下是能力检查结果与日常同步状态的对应摘要；完整的行为规则与 APR/额度缓存两张表见[数据状态规则](DATA-STATES.md#api-结果状态与持仓产品降级规则)。请求完整性与单产品资料完整性分开：分页完整、身份可识别，但某款产品缺少 APR/额度时，请求仍可成功，产品行单独提示缺失。

| 请求结果 | 定义 | 页面与目录处理 |
|---|---|---|
| `complete + returned`（有数据） | 请求成功、分页完整、必要身份字段可用，并返回一条或多条范围内记录。单产品 APR/额度是否有效另行判断。 | 显示可确认资料；APR/额度缺失时匹配同身份有效缓存，无缓存按产品资料模式提示。只有计算必需资料完整时才参与收益，利率/额度方案不完整时整款排除机会指标。 |
| `empty`（成功但空） | 请求成功且完整，但没有范围内记录。 | 无产品且无达标持仓：不建行、不报错。若持仓产品身份可识别且超过该资产门槛：保留/创建行；匹配到旧 API 产品时沿用有效字段缓存，否则缺失提示按整款产品资料模式显示。 |
| `partial`（部分返回） | 整份请求结果不完整：分页未完成、查询范围不全，或必要身份/持仓金额异常导致行无法安全识别和合并。多请求汇总中一部分失败也记为部分成功，但不改写已完整请求的状态。 | 显示“部分数据未返回”；保留已有产品、已知持仓和有效字段缓存，不把缺行推成零、不据此归档。单个产品 APR/额度异常本身不代表请求部分返回。 |
| `error`（请求失败） | 请求被拒绝、网络/HTTP/API 错误、鉴权失败等，且没有可用的完整结果。 | 显示“API 暂不可用”；保留已有产品、已知持仓和缓存，不当成空、不据此归档。 |
| `not_configured`（未配置） | 该范围需要私有凭证，但账号没有可用配置。 | 显示未配置；不能当成零持仓。公开 API 可独立检查，不受此状态影响。 |
| `unsupported`（项目没有可用接口） | 按当前项目范围找不到可用端点，或可用端点明确拒绝该范围。 | 产品/APR或持仓改为手动维护；不是运行时错误，不反复重试无用接口。 |

补充约束：

1. 产品和持仓是两种独立能力，分别配置、分别记录状态；一边成功不替另一边背书。
2. 持仓产品身份可识别且超过目录门槛时，即便产品列表成功为空也保留/创建对应行。匹配到旧 API 产品时沿用该身份下有效 APR/额度缓存；无可用缓存时按整款产品资料模式显示“未获取”或“待填写”。
3. 只有币种汇总余额且同币种有多条产品时，不能识别具体产品，不把余额拆到多行；若当前项目该币种只跟踪一条产品且汇总范围匹配，可一对一映射。
4. API 产品的活跃目录条件为：USDT、USDC、USDGO 持仓严格大于 `0.01`，或 APR ≥ `6%` 的活期/期限不超过 7 天定期；BTC 保持原持仓门槛（>0），APR 门槛不变。手动产品保持现有规则。非 BTC 前端说明简述 API 门槛；手动产品例外见[数据状态规则](DATA-STATES.md#目录与身份)。
5. VIP、下线或未达到门槛的无持仓 API 产品不进入有效机会目录；达标持仓优先保留并标明资格/状态。已有 API 产品只有在数据完整且能确认持仓、APR 两种条件都不满足时才归档；未知或不完整数据不作为低于门槛的证据。
6. 明确返回的有效持仓可保留；只有完整、权威的持仓结果能将缺行判零。自动归档要求完整数据确认产品不满足持仓与 APR 两类目录门槛。USDT、USDC、USDGO 持仓 `≤0.01` 已不满足持仓门槛，不要求必须为零；BTC 与手动产品沿用既定规则。用户手动“移除产品”的零持仓限制是另一项操作，不与自动归档混用。归档保留历史，不物理删除；失败、部分、未配置或身份不明均不能作为归档依据，完整规则见[目录与身份](DATA-STATES.md#目录与身份)。
7. `holdingEmptyMeansZero` 是逐端点配置的判定，不从 HTTP 200 或空数组自动推断。同步路由用同一配置生成可判零的精确“账号 × 币种 × 活期/定期”范围；未标记为“可以”的范围不会补 0，也不会据此归档。Binance、Bitget、Bybit Global 还必须满足范围正确、身份完整且所有分页完整；OKX 则必须返回有效数组、可识别币种、无受监控币种重复行且金额有效；Bybit EU/MEXC 无产品级持仓 API。

## 代码落实情况

- **适配器与能力配置：**`lib/platform-capabilities.ts` 是日常接入状态、查询路径、权限、官方文档及持仓空结果判零依据的代码来源；新能力仍需人工审核后加入，不会自动发现未知端点。
- **同步与目录：**Binance、Bitget、Bybit、OKX 已区分完整、部分、失败的关键持仓结果；Bybit 目录/持仓扫描会跟随接口返回的 cursor，游标重复、下一页失败、必要身份或持仓金额异常时标为部分，不能当成功空。可识别产品的 APR/额度缺失只影响该行字段有效性，不等同于扫描不完整。目录按稳定产品身份匹配，Bitget 和 Bybit 定期身份包含期限。缺行补零及以缺行为依据的归档共用逐项能力配置的判零闸门；本轮明确返回的有效持仓按资产门槛判断，不把低于门槛的正数改写为零。
- **OKX 汇总余额：**日常同步更新 USDT、USDC、BTC。虽然接口不含产品 ID，但项目每币种只跟踪一条活期产品；有效完整数组中缺少该币种时补零并解除旧缓存标记。响应字段异常、币种不可识别、目标币重复行或金额无效时不补零，沿用已知缓存并标记部分结果。
- **检查 API：**报告现为 112 条自足 `checks` 记录，分别列出产品/APR 与持仓；每条带平台、地区、币种、期限、信息项、API 支持、最近结果、接口方式、方法/路径、权限、官方文档、检查时间、日常接入状态及持仓空结果判零依据。`apiSupport` 来自经过核验的项目接口配置，不随一次请求是否为空、是否失败或是否配置凭证而改变；最近结果单独记录。鉴权持仓只显示“接口调用成功 / 部分返回 / 请求失败”等状态，不输出是否非空、行数、持仓产品 ID、正持仓判断或金额；公开产品目录可保留产品行信息。MEXC 的 PH/UK 依据放在同一平台记录的地区子项中。检查器不自动发现未知端点，不写入产品、持仓、缓存或历史；不请求 OKX On-chain Earn。
- **API 设置弹窗：**区块顺序为“配置 API → 手动刷新频率 → API 检测”。检查按钮默认“检测 API”，报告生成后短暂显示对勾，3 秒后恢复；JSON 下载保留到下一次检查开始。整体检查失败时显示失败提示，不显示成功对勾或下载。
- **回归测试：**自动化测试覆盖能力矩阵、分页完整性、空/部分/失败、APR/额度字段、产品身份、零值归档边界、MEXC 合并报告及 API 检测按钮状态。每次发布前按当前分支的测试结果记录本次审查，不在能力说明中保留旧测试次数或部署状态。

## 复查与新能力发现

已接入端点可在日常同步时观察其已知返回；未被代码调用的未知端点，不会因为日常刷新而自动发现。检查 API 也只验证代码和文档已知的端点。新增交易所能力仍通过后续官方 API 文档复核，再人工更新能力矩阵、适配器和测试；一次检查结果不会自动启用接口。
