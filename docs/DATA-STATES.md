# 数据规则与测试

## 数据来源

- `productDataMode`：产品信息由 API 或人工维护。
- `holdingDataMode`：默认持仓来源；`holdingSourceIds` 标记实际采用的 API 持仓。API 返回值及其缓存只读，不能因产品信息需要人工填写就开放持仓编辑。
- `rateCoverage`：`complete`（完整）、`base_only`（仅基础 APR）、`max_only`（仅最高 APR）、`unavailable`（不可用）。

产品与持仓分别判断。持仓的正数、明确零、未知不能混用；只有完整持仓快照才能把未出现的产品判为零。产品字段缺失不抹掉已知持仓，持仓失败不抹掉有效产品数据。

## 目录与身份

适配器返回候选数据，`lib/product-catalog.ts` 统一维护用户目录；查看态、编辑态和顶部指标使用同一活跃目录。

| 候选产品 | 目录规则 |
|---|---|
| API 活期机会 | APR ≥ 6% |
| API 定期机会 | APR ≥ 6%，且期限 ≤ 7 天 |
| 已有正数持仓 | 保留，不受机会门槛、期限或申购资格影响 |
| API 信息从未有有效 APR | 不创建占位产品 |
| API 仅提供持仓、产品信息需人工维护 | 正数持仓时创建待补全项；零持仓不创建 |
| 用户手动添加 | 保留到用户删除 |
| 明确停售或不合资格 | 已知零持仓可归档；未知持仓不据此清除已有行 |
| 单次失败或产品缺失 | 不据此自动归档 |

种子模板只用于匹配、演示和测试，不预置进真实用户目录。历史占位清理使用一次性迁移，不增加运行时特殊分支。

平台原始 ID 用于对应上游产品；内部 `identityKey` 用于关联同一产品；`identityFingerprint` 区分同一产品的新一期。普通 APR/额度调整不新建行，定期申购窗口或期限变化会生成新一期。旧期有持仓时保留；用户删除旧期不阻止新期出现。归档保留数据库记录，不等于物理删除。

## 两列状态与计算

| 状态 | 页面处理 | 收益/机会指标 |
|---|---|---|
| 产品完整，持仓已知 | 展示产品信息及持仓摘要 | 正数持仓参与收益 |
| 产品仅基础/最高 APR | 显示已知 APR 和具体缺失项 | 不算收益；APR 可比较；不算未知额度 |
| 人工字段缺失 | “APR/额度/期限/买入日待填写” | 不算收益 |
| API 字段不可用 | “待获取”，保持只读 | 不算收益 |
| 产品失败但有缓存 | “产品信息沿用 … 的缓存数据” | 用缓存产品数据计算 |
| 持仓失败但有缓存 | 保留金额，“持仓沿用 … 的缓存数据” | 产品完整时用缓存持仓计算 |
| 未配置持仓 API、无缓存 | “持仓未获取”；原因“未配置 API；配置后可同步持仓” | 不算收益和剩余额度 |
| 持仓失败、无缓存 | “持仓未获取”；原因“API 同步失败” | 同上 |
| 稀疏接口无明确结果 | “持仓未获取”；原因“接口未返回该产品持仓” | 同上 |
| 明确零持仓 | 展示金额与已知额度，查看态统一弱化 | 无收益，可比较额度 |

产品不完整时，持仓列保留金额及缓存提示，不显示进度条或剩余额度。编辑态使用输入/只读框，不在其下重复孤立金额。两列不互相重复错误原因。

资格要求只作说明，不使用复选框、不自动推断用户资格。到期后显示“已到期 N 天”，保留原 APR，用户自行管理。定期/限时产品缺买入日会阻止收益计算，不阻止比较 APR 和已知额度。

| 顶部指标 | 计算范围 |
|---|---|
| 总持仓 | 活跃目录内已知金额 |
| 组合有效 APR、预计每日收益 | 产品完整且持仓大于零；APR 按实际阶梯占用加权 |
| 最佳首档 APR/最高公开 APR | 活跃目录内 APR 已知的产品，不要求持仓、买入日或资格确认 |
| 高息剩余额度 | APR ≥ 6%，首档/申购额度与持仓均已知；包含定期 |
| 超出首档 | 首档上限及持仓已知 |

删除有二次确认，先改编辑草稿；保存后生效，取消编辑则恢复。

## 同步与时间

上海时间每天 07:00 自动更新。失败或部分成功时，等 3 分钟进行最后一次尝试（实际完成时间包含请求耗时与投递延迟）。每天首次打开已登录页面另刷新一次，成功失败均计次；按账号、上海日期在服务器记录，多设备共用。主动点击手动刷新保留原冷却设置，不执行分钟级重试；每日打开刷新不占用手动按钮的冷却。

Cron 只向 `SYNC_QUEUE` 投递每个用户的任务，队列每次仅消费一条（`max_batch_size: 1`），最多重试一次。不能在同一次 Worker 调用中等待后重复同步，也不能把多个用户合并消费，否则会共享外部请求额度。消费并发为 1；队列任务只含用户标识与计划时刻，不含密钥或资产数据。

重试开始前若本时段已有提交的数据或已记录自动任务最终失败，则跳过；超过下一计划时段的旧任务也跳过。`sync_snapshots` 保存结果，`refresh_control` 原子记录每日打开刷新和账号级运行锁，避免浏览器、队列互相覆盖。页面遇到后台重试窗口先等待，结束后再尝试当天首次打开刷新；等待不会提前占用当天次数。首次无缓存也走同一入口，不另发首次同步。单个用户一次同步仍受运行平台限制。

| 同步结果 | 保存与提示 |
|---|---|
| 重试中 | 中间候选不提交；显示“正在更新”，已有目录和持仓保持可见 |
| 首次重试中、无缓存 | 显示“暂无成功数据。正在更新中，请稍候。”与骨架屏，不提前显示最终失败 |
| 完全成功 | 目录和缓存同批提交，清除失败提示 |
| 最后一次部分成功 | 提交部分结果，按平台/币种/接口提示具体失败 |
| 最后一次全部失败 | 保留缓存，统一提示“产品和持仓数据更新失败” |
| 手动刷新冷却 | 不请求交易所，不清除上一轮失败或缓存提示 |
| 浏览器读取失败 | 提示页面/网络读取失败，不推断交易所失败 |

页面每分钟检查缓存，编辑时暂停。只有本次打开的每日刷新仍在等待时，才继续申请一次每日刷新；完成后轮询只读缓存，即使页面跨天保持打开也不会自动再刷。到 07:00、尚未收到本轮结果时，与后台进行中、页面等待及页面刷新统一显示“正在更新中”，不提前显示下次计划时间；最终结果沿用成功/部分失败/全部失败的提示。计划尚未启动、任务中断和运行锁保留 15 分钟超时保护，避免永久等待；正常情况下第二次尝试结束即结束后台更新提示，不必等满 15 分钟。

个人保存数据（手动产品、持仓、补填字段和隐藏记录）读取失败不按空数据处理：提示“服务器读取失败，数据无法显示，请刷新页面。”，不提供独立重试按钮。首次未加载成功时保留六项统计布局，数值用“—”占位；产品行使用同文案的表格空状态，禁止编辑、暂停轮询及前端持仓回写。读取成功后恢复正常展示和轮询。

本地预览可用 `/private/home?syncScenario=personal-error` 模拟个人数据读取失败；该参数不会在生产环境启用。

**时间按数据自身来源保留：**产品使用原始 `rate.fetchedAt`；持仓连续失败继承原 `holdingFallbacks`，不能替换成整轮 `updatedAt`。缓存提示不根据错误文案猜测。页面读缓存不写持仓表；只有新刷新结果中实际取得的持仓（包括零）才保存，平台整体成功/失败不能替代单条持仓的新旧判断。

## 验证方式

### 同步诊断日志

部署后在 Worker 的 Observability / Events 中查找 `sync_finished`。用 `runId` 关联一次任务，用 `userRef`（用户 ID 的哈希化标识，不是邮箱）区分用户；`trigger` 区分 `scheduled`（后台）、`daily`（每天首次打开）、`manual`（点击按钮），`attempt` 是自动任务轮次。普通页面轮询不产生同步诊断日志。

- `sync_platforms`：各平台最终状态，全部失败抛错前也会记录。
- `exchange_http`：接口、币种（请求明确指定时）、HTTP 状态或网络/超时原因、耗时；`requestAttempt` 区分接口内短重试。运行时明确报请求超限时记为 `subrequest_limit_exceeded`，不根据耗时猜测。
- `exchange_payload` / `exchange_body_error`：通过 `requestId` 对应 HTTP 请求，记录数字业务码或正文读取失败类型。HTTP 200 不等于业务成功。
- `platform_read_error` / `sync_finished`：平台读取异常、整轮成功/部分成功/失败与是否提交缓存。
- `sync_retry_queued` / `sync_skipped`：安排下一轮的延迟，或跳过已完成/过期任务的原因。

403/451/429 的 `accessReason` 从响应中识别 `region_restricted`（地区限制）、`rate_limited`（频率限制）、`ip_not_allowed`（IP 不允许）；没有明确依据时为 `access_denied_unknown`，不能仅凭 403/451 判定地区限制。成功和失败响应均可附带经过格式校验的 `cf-ray`、`x-request-id`、`x-amz-cf-id`，用于对比和上游追踪；未返回或格式不符时省略。这些标识不等于实际出口 IP 或位置，也不额外请求查 IP 服务。

耗时单位为毫秒；HTTP 耗时截至响应返回，正文日志耗时包含读取。日志不输出完整 URL、认证头、签名、密钥、邮箱、持仓金额或响应正文。未识别的主机、路径和非数字业务码使用占位值。原因识别只在内存中检查响应，不保存原文；部署前丢失的诊断无法补回。排查队列失败时也检查 `sync_queue_finished`，以免漏掉同步开始前的数据库异常。

### 离线与本地验证

`npm test` 运行离线测试，`npm run check` 另包含静态检查与构建。测试用内存数据库和模拟交易所响应驱动真实同步路由，不访问线上账号；覆盖连续失败、恢复、首次同步、冷却、字段完整性及机会门槛。

启动本地开发后，`/private/home` 包含产品与持仓的完整状态样本。可加 `?syncScenario=partial`，切到 **USDC** 查看专项模拟：Bitget 持仓沿用固定时间 `09/05 08:56`，整轮更新时间变化也不会改写它。

其他 `syncScenario` 值：`error`（全部失败）、`success`（恢复成功）、`syncing`（有缓存更新中）、`initial-syncing`（首次更新中）、`initial-error`（首次失败）。这些参数只在本地开发预览生效，不写数据库；静态页面场景用于观察样式，连续状态变化由自动化测试验证。
